# Oracle Cloud native deployment

Exact steps to deploy Veritech Scan to a single Oracle Cloud **Always Free**
ARM64 (Ampere A1) Ubuntu 24.04 VM, running entirely as **native systemd
services** — Caddy, PostgreSQL, Redis, the FastAPI API, the Dramatiq
worker, and Next.js are all installed directly on the host. There is no
Docker, no containers, and no container runtime anywhere in this stack.

> **Provision and deploy on the VM itself.** `scripts/install-server.sh`
> installs Chromium's OS dependencies and verifies a real Chromium launch
> on the host. This must happen on the real ARM64 target — cross-building
> or emulating for `arm64` from an x86 machine is not a supported path for
> this project (same reasoning as before, just without Docker in the
> picture: Playwright's `--with-deps` resolves an architecture-specific
> package set, which only means something run natively on the target).

## 1. Provision the Ubuntu 24.04 ARM64 VM

In the Oracle Cloud console: **Compute → Instances → Create Instance**.

- Image: **Canonical Ubuntu 24.04** (Minimal or default, ARM64/Ampere).
- Shape: **VM.Standard.A1.Flex** (Always Free eligible — up to 4 OCPU / 24GB
  total across your Always Free A1 instances).
- Networking: create/use a VCN with a public subnet.

## 2. Create a public IP

Assign a public IPv4 address to the instance during creation (or attach a
reserved public IP afterward via **Networking → IP Management**). Note this
IP — it's what `app.veritechdiligence.com` will point to.

## 3. Configure SSH key access

Provide your SSH public key during instance creation. Confirm you can
connect:

```bash
ssh ubuntu@<public-ip>
```

## 4. Run `install-server.sh`

Copy the repo (or just the `scripts/` directory) to the VM and run the
install script as root. It installs Caddy, PostgreSQL, Redis, Python 3.12 +
venv tooling, Node.js 22, Chromium's OS dependencies, creates the
`veritech_scan` Postgres database + role, creates a non-root deploy user
(`veritech` by default) with a **scoped** sudoers grant (only
`systemctl restart/stop/start/status` on this app's three units plus
`caddy reload`/`validate` — never full root), and configures UFW:

```bash
scp -r . ubuntu@<public-ip>:~/veritech-scan-bootstrap
ssh ubuntu@<public-ip>
sudo ~/veritech-scan-bootstrap/scripts/install-server.sh
```

Review `scripts/install-server.sh` before running it — like the previous
Docker-based bootstrap script, every destructive/irreversible step prompts
for confirmation unless `--yes` is passed, and it prints SSH-hardening
guidance at the end rather than applying it automatically.

The script prints a generated PostgreSQL password at the end (also saved to
`/opt/veritech-scan/postgres-password.txt`, mode `600`) — you'll need it for
step 6.

## 5. Clone the private repository

As the deploy user created in step 4:

```bash
sudo -iu veritech
mkdir -p /opt/veritech-scan && cd /opt/veritech-scan
git clone git@github.com:<your-org>/veritech-scan.git app
cd app
```

(Set up a deploy key or SSH agent forwarding for the private repo
beforehand.)

Re-run `sudo ./scripts/install-server.sh --yes` once the repo is cloned —
this installs the systemd units and Caddyfile from `deploy/` (it skips that
step on the first pass, before the repo exists).

## 6. Configure `.env.production`

```bash
cp .env.example .env.production
```

Edit `.env.production` and set at minimum:

```
APP_ENV=production
APP_DOMAIN=app.veritechdiligence.com
APP_URL=https://app.veritechdiligence.com
MARKETING_SITE_URL=https://veritechdiligence.com

POSTGRES_DB=veritech_scan
POSTGRES_USER=veritech_scan
POSTGRES_PASSWORD=<from install-server.sh's output — step 4>
DATABASE_URL=postgresql+psycopg://veritech_scan:<same-password>@127.0.0.1:5432/veritech_scan

REDIS_URL=redis://127.0.0.1:6379/0

JWT_SECRET=<generated — step 7>
INITIAL_ADMIN_EMAIL=<your admin email>
INITIAL_ADMIN_PASSWORD=<generated — step 7>

ARTIFACT_STORAGE_LOCAL_PATH=/opt/veritech-scan/artifacts
PLAYWRIGHT_BROWSERS_PATH=/opt/veritech-scan/ms-playwright
```

Note both Postgres and Redis are addressed via `127.0.0.1` — they are
installed to listen on localhost only and are never reachable from outside
the VM (verify with `sudo ss -tlnp | grep -E '5432|6379'` — both should show
`127.0.0.1`, never `0.0.0.0` or a public IP).

## 7. Generate secure secrets

```bash
openssl rand -base64 48   # -> JWT_SECRET
openssl rand -base64 24   # -> INITIAL_ADMIN_PASSWORD
```

(`POSTGRES_PASSWORD` was already generated by `install-server.sh` in step
4 — reuse it rather than generating a new one, unless you also rotate it in
Postgres itself.)

Never commit `.env.production`. It's already covered by `.gitignore`. Once
its values are copied into `.env.production`, delete
`/opt/veritech-scan/postgres-password.txt`.

## 8. Run the deploy workflow

```bash
cd /opt/veritech-scan/app
./scripts/deploy.sh
```

This is the full native deploy pipeline:

1. `git fetch` / `git pull` the target branch (default `main`).
2. Create/update the Python virtualenv at `/opt/veritech-scan/venv` and
   install `apps/api/requirements.txt` into it.
3. Re-verify Chromium still launches with the installed dependency set
   (`python -m app.worker_check --startup-only` — the same fail-fast check
   that used to run at Docker image build time, now run at deploy time).
4. `npm ci` in `apps/web`.
5. `npm run build` in `apps/web`.
6. `alembic upgrade head` against `DATABASE_URL` from `.env.production`.
7. Sync `deploy/systemd/*.service` to `/etc/systemd/system/` and
   `deploy/caddy/Caddyfile` to `/etc/caddy/Caddyfile`, validate the
   Caddyfile, and `systemctl daemon-reload`.
8. Restart `veritech-scan-api`, `veritech-scan-worker`, and
   `veritech-scan-web`, and reload Caddy.
9. Run `scripts/healthcheck.sh prod` — Caddy, API, web, worker, Postgres,
   Redis, and Chromium — printing recent `journalctl` output and exiting
   non-zero if anything fails, without leaving the deploy half-applied.

Also available as `make deploy`.

## 9. Bootstrap the admin user

```bash
cd /opt/veritech-scan/app/apps/api
/opt/veritech-scan/venv/bin/python -m app.seed --admin-only
```

(Also available as `make seed VENV=/opt/veritech-scan/venv ARGS=--admin-only`.)

## 10. Configure DNS

- `veritechdiligence.com` — leave exactly as-is on **GitHub Pages** (this
  repository does not touch the marketing site).
- `app.veritechdiligence.com` — create an **A record** pointing at the VM's
  public IP from step 2 (and an **AAAA record** if the VM has a public
  IPv6 address).

DNS propagation can take a few minutes to a few hours depending on your
registrar's TTL.

## 11. Verify Caddy TLS certificate issuance

Once DNS resolves to the VM, Caddy (running as its own systemd unit,
`caddy.service`, installed by the `caddy` apt package) automatically
requests a certificate from Let's Encrypt on first request to
`app.veritechdiligence.com`. Check:

```bash
curl -vI https://app.veritechdiligence.com/health
sudo journalctl -u caddy --no-pager | grep -i certificate
```

If issuance fails, confirm DNS has propagated and that ports 80/443 are
reachable from the public internet (Let's Encrypt's HTTP-01 challenge needs
port 80 open, which `install-server.sh` already configured via UFW).

## 12. Verify application, API, worker, Postgres, and Redis health

```bash
./scripts/healthcheck.sh prod
# or: make healthcheck MODE=prod
```

This checks that `veritech-scan-api`, `veritech-scan-worker`,
`veritech-scan-web`, and `caddy` are all `active` under systemd, Postgres
readiness, Redis `PING`, the API's `/health` endpoint (which itself
verifies Postgres + Redis connectivity from the API's perspective), the web
app responding on `127.0.0.1:3000`, a real worker check (queue/actor
registration + a real Chromium launch), and the public HTTPS endpoint
through Caddy.

Also confirm the full user flow: open `https://app.veritechdiligence.com`,
sign in with the admin account from step 9, and check `/scans` for the
seeded demo scan (`make seed` without `--admin-only` if you want the
synthetic demo data too).

## 13. Update and rollback procedures

**Update / deploy a new release:**

```bash
cd /opt/veritech-scan/app
./scripts/deploy.sh main
```

**Rollback to a prior release:**

```bash
git checkout <prior-commit-or-tag>
./scripts/deploy.sh --no-pull
```

This reinstalls dependencies, rebuilds the Next.js bundle, and re-runs
migrations from the checked-out (older) commit (Alembic migrations in this
project are additive/forward-only by convention — a rollback to older
*code* against a newer *schema* is a case-by-case judgment call; always take
a fresh `make backup-db` before rolling back a release that included a
migration), then restarts services.

## What's different from the old Docker Compose setup

- Every service is a systemd unit (`deploy/systemd/*.service`) instead of a
  container — `systemctl status/restart/stop` and `journalctl -u <unit>`
  replace `docker compose ps/restart/logs`.
- Postgres and Redis are native apt packages bound to `127.0.0.1`, not
  containers with `expose:`-only networking — the isolation guarantee is
  the same (never reachable off-box), just enforced by the daemon's own
  bind address instead of container networking.
- Caddy is the native `caddy` apt package (its own systemd unit), reading
  `/etc/caddy/Caddyfile` — content is unchanged from the old container
  Caddyfile except upstreams point at `127.0.0.1:8000`/`127.0.0.1:3000`
  instead of Docker's internal DNS names (`api`/`web`).
- There is no image build step. `scripts/deploy.sh` installs dependencies
  directly into a long-lived virtualenv (`/opt/veritech-scan/venv`) and
  `node_modules`, rather than building an immutable image layer per deploy.
- Chromium's fail-fast launch check moved from a Docker build-time `RUN`
  step to `scripts/deploy.sh` step 3, running against the real host
  environment either way.
